# Work IQ MCP: employee rollout within one Entra tenant

## Scope and evidence boundary

Researched **2026-10-29 UTC**. Target: employees of **one organization**, using its existing Entra tenant and a customer-owned OAuth application through Speakeasy. This is not a SaaS integration serving multiple customer tenants. Read `guides/work-iq/external.md`, `speakeasy.md`, `research.md`, and `meta.yaml`; this report does not modify them.

**Evidence labels:** **Documented** = live primary Microsoft documentation fetched with Python/curl (HTTP 200); **Pilot** = transferred observations in this repository, not independently reproduced; **Recommendation** = operational design derived from the cited documentation; **Unresolved** = no sufficient Work IQ-specific evidence or live tenant test. No sign-ins, paid requests, tenant changes, or business-data reads were performed. Microsoft Learn's generic authorization banner appeared on some pages, but article bodies were publicly returned and inspected. The licensing PDF was downloaded and pages 13–14 extracted with `pypdf` in a temporary environment outside the repo.

## Executive decisions

1. **Keep a single-tenant app and tenant-specific OAuth endpoints.** Employee count does not make an application multitenant. “Accounts in this organizational directory only” is the appropriate audience; enforce an employee-only assignment group because a home tenant can also contain guests. [S9, S10, S11]
2. **Share configuration, not employee credentials.** One approved client registration and client secret can identify the confidential OAuth client; every employee must authorize their own delegated session. Retain Speakeasy **User Identity**, never distribute a pilot user's access/refresh token or substitute a shared service account. Work IQ operates on behalf of the signed-in user; application-only authentication is unsupported in the documented Foundry integration. Speakeasy's actual session isolation remains a release test, not a Microsoft-validated product claim. [S5, S6]
3. **Use rollout groups, then explicitly expand to employees.** Billing audiences, enterprise-app assignments, catalog availability, and Speakeasy access are different controls. Keep their intended populations aligned, but do not claim that configuring one sets the others. Billing supports All users or selected groups; enterprise-app group assignment needs Entra ID P1/P2 and does not expand nested groups. [S1, S2, S7, S10, S11]
4. **Use approved tenant-wide delegated consent plus assignment for employee scale**, rather than generating a principal-specific consent grant for every employee. Tenant-wide consent is not app-only permission, billing enrollment, or assignment; it does not remove each employee's sign-in. Keep `WorkIQAgent.Ask`'s broad read/write warning. [S5, S6, S10, S12]
5. **Do not publish a universal per-user catalog-install requirement or a universal admin-install replacement.** Microsoft documents admin installation for *plugins and skills*, but that does not establish that the unified Work IQ MCP requires that package installation, or that assigning its catalog item replaces self-installation for direct Speakeasy access. Capture the actual tenant item and verify with a newly onboarded employee. [S3, S4, S7; Pilot]
6. **Do not bulk-buy Copilot licenses from the pilot or an entitlement error.** The current October 2026 Credits Guide says Work IQ APIs can run on behalf of any Microsoft 365 user and are not Copilot-license entitlements, while the live Foundry quickstart still requires a Microsoft 365 Copilot license per user. Resolve the applicability of this discrepancy before committing organization-wide eligibility or purchases. [S5, S8]

## Catalog deployment: what is actually documented

### Distinguish four different surfaces

- **Unified remote service:** use `https://workiq.svc.cloud.microsoft/mcp`. Workload-specific Calendar/Mail/Teams/etc. MCP servers are legacy and should not be used for new production projects. This is not a fleet of locally installed servers. [S3, S4]
- **Foundry project catalog:** Tools → Tools tab → Connect a tool → Catalog → Work IQ MCP → Create creates a *project tool connection*, followed by OAuth configuration and user sign-in. This is authoritative for Foundry, not a self-install URL for an employee using Speakeasy. [S5]
- **Microsoft 365 admin registry:** Agents → Tools provides registry discovery, requests, and governance. Its existence does not prove installation in each employee account. [S7a]
- **Plugin/skill deployment:** Microsoft explicitly documents Agents → Tools → select plugin/skill → Install → **All users** or **Specific users or groups** → review → Install. It also documents plugin user availability under Agents → Tools → Plugins → Users. These are real admin distribution capabilities, but the article's installation procedure is scoped to **plugins/skills**, not a guarantee for every standalone MCP entry. [S7]

**Recommended replacement for the pilot installation section:** describe tenant approval/availability and employee onboarding as a deployment decision. If the tenant's unified Work IQ entry is an installable plugin/skill, document the verified admin deployment path and selected employee groups. If it is only an MCP registry item, follow the MCP approval/consent/governance workflow instead; do not relabel plugin installation as MCP assignment. Do not present either as a substitute for the separate OAuth client consent or billing steps. [S5, S7]

**Unresolved blocker:** the original pilot reports reads succeeding after a user installed the unified item, despite billing already being enabled; no exact self-install link was captured, and simultaneous backend changes were not excluded. The live Work IQ overview, enablement guide, and Foundry quickstart inspected here do **not** establish a universal additional employee catalog-install prerequisite. They document tenant enablement, service-principal provisioning, billing, and delegated OAuth. Absence of an install step is not proof that it is unnecessary in every tenant. Obtain Microsoft confirmation or compare two fresh employee accounts before deleting the check. [S3, S5, S13; Pilot]

## Billing audience and licensing

**Documented audience:** initial activation defaults to the entire organization; choose **Customize setup configuration** before activation to narrow it. In policy scope, **All users** is default; switch to **Specific groups** and select directory groups for staged deployment. The current policy article says specific users/resource accounts must be included through security groups, so replace the guide's ambiguous “pilot user, or group if required” instruction with the current group workflow. [S1, S2]

**Recommended employee design:** start with a directly populated employee rollout security group; extend by department/wave after the acceptance gates below. Use All users only after explicitly accepting its broader tenant population, including any nonemployee accounts eligible under other controls. Retain service-specific selection (**Work IQ API for custom apps and agents**, verify displayed label), keep **Auto-apply new services** off unless separately approved, and set realistic policy and per-user credit limits and administrator/user alerts. Microsoft documents that additional policies have independent limits rather than inheriting the default policy's tenant-level limit; do not describe the default as a universal cap across all policies. Reconcile existing/overlapping policies and monitor actual policy selection before expanding. [S1, S2]

**Documented pricing/licensing:** October 2026 Credits Guide p. 14 states “on behalf of any Microsoft 365 user”; prerequisites are tenant enablement and Copilot Credits usage-based billing, and Work IQ APIs are not included as Copilot-license entitlements. Page 13 separates variable chat/context consumption from static tools/action consumption (0.1 credits per API call in this edition). Do not equate one MCP request with one credit or treat all nested backend work as a single charge. [S8]

**Unresolved per-user requirements:** the live Foundry quickstart separately says “A Microsoft 365 Copilot license for each user who calls Work IQ through your agent.” This is a genuine documentation conflict, not a proven universal Work IQ MCP requirement and not conclusively a Foundry-only exception. The Credits Guide is newer licensing guidance but cannot prove tenant entitlement implementation. Confirm with Microsoft for the specific direct-MCP scenario; inventory each employee's Microsoft 365/workload access rather than assuming billing creates Exchange, Teams, SharePoint, or other underlying access. Work IQ requests remain scoped to user permissions and tenant policy. [S5, S6, S8]

## Authentication, consent, and assignment

### One registration; many independently authenticated users

Keep the app registration single-tenant; the common Microsoft-hosted MCP URL does not imply a multitenant client registration. Keep tenant-specific authorize/token URLs and the exact Speakeasy deployment's Web callback. The Work IQ Foundry quickstart documents tenant-scoped endpoints, a client secret, `WorkIQAgent.Ask offline_access`, and a Web redirect URI; it must not be copied as a Speakeasy UI walkthrough. [S5, S9]

**Recommendation:** manage the OAuth client secret centrally with an owner, expiry/rotation procedure, and approved secret storage; employees should not receive it. Employee authentication produces their own delegated authorization; do not copy the pilot connection's tokens into a shared server identity. Retain User Identity and independently test two employees, refresh, logout, and offboarding. Microsoft sources support the delegated security model, not Speakeasy's implementation or `client_secret_post` selection: that method, the callback used in the source pilot, and private-server behavior remain **Pilot** evidence until validated in the deployed Speakeasy version. [S5, S6; Pilot]

### Tenant-wide consent does not mean unrestricted access

`WorkIQAgent.Ask` is delegated, admin-consent-required, and includes read **and write** access to Microsoft 365 resources available to the signed-in user. Do not claim a read-only setup because smoke tests use `fetch`; preserve explicit administrator risk approval. [S6]

For rollout, replace the one-person `consentType: Principal` example with the admin-center **Grant admin consent** workflow, or a separately reviewed Graph example using `consentType: AllPrincipals`, no user-specific `principalId`, and service-principal object IDs for `clientId`/`resourceId`. Inspect existing grants before modifying them; do not blindly create duplicates or delete shared resource principals. Microsoft documents tenant-wide delegated consent separately from application-permission app-role assignments. Do not introduce Graph application permissions as a substitute. [S12]

Keep **Assignment required = Yes** on the customer enterprise application and assign employee wave groups. Tenant-wide consent approves scopes for users; assignment determines which users may sign into the app. Group-based enterprise-app assignment requires P1/P2 and excludes nested membership. Direct user assignment is an alternative if group assignment is not licensed. Single-tenant alone does not mean employees only; Assignment required = No also permits invited external users, and Global Administrators can bypass the assignment-required restriction. Use ordinary employee identities for both positive and negative tests. [S9, S10, S11]

## Release gates and remaining blockers

1. **Catalog gate:** capture exact unified item identity/type, tenant-approved install/distribution route, and fresh-employee results. Demonstrate whether admin deployment replaces self-installation or Microsoft confirms no install is required for direct MCP. [S5, S7; unresolved]
2. **Eligibility gate:** obtain Microsoft clarification of Credits Guide vs Foundry licensing, and confirm each release cohort's workload access and service availability. Do not remediate `notEntitled` by speculative license purchases or broader grants. [S5, S6, S8; unresolved]
3. **Identity gate:** ordinary users A/B each authorize separately; `/me` and accessible data reflect A/B respectively, never the pilot/admin; an unassigned employee and guest cannot connect; validate refresh, revocation/offboarding, and no token leakage in logs. Speakeasy token isolation and access controls require deployment-specific verification. [S5, S6, S10, S11; proposed tests]
4. **Cost/safety gate:** confirm a new employee's effective spending policy and attribution, limits/alerts, and explicit write-tool policy. A broad delegated scope is not read-only; monitor a small cohort before All users. [S1, S2, S6, S8; proposed tests]

**Critical blockers are evidence gaps, not a need for a multitenant app:** unknown unified catalog install semantics, conflicting per-user licensing guidance, and untested Speakeasy employee isolation/distribution/refresh. The safe architecture is otherwise clear: one single-tenant confidential client, approved delegated tenant consent, employee access assignments, appropriate billing audiences, and separate user sessions.
